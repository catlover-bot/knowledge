# テーマから読む

月別・年別の記録を、「何を知りたいか」から引けるようにした入口。以下の読み順は、このリポジトリのメモを組み合わせた編集上の案である。元の記録は移動せずに残している。

**横断ノート**は複数の資料を比較して、判断に使える区別・確認項目をまとめたもの。**読書記録**は当時の要約や考察であり、製品の現行仕様や論文の主張を保証するものではない。数値や実装条件を使うときは、各項目の一次資料と確認日も読む。リンク先の項目が閉じている場合は、その見出しを開く。

## すぐ使う横断ノート

- [生成した証明は何を検証すればよいか](formal-proof-validation.md)：定理文・依存する公理・検証環境を分け、コンパイル成功から何が言えるかを整理する。
- [LLMによるコード最適化を公平に比較するには](code-optimization-evaluation.md)：正しさ、実行時間、コードサイズを混同しない評価の組み立て方。
- [見た目の3Dモデルと編集できるCADを選び分ける](cad-representations.md)：メッシュ、編集可能な生成手順、幾何制約の違いから出力と検査方法を選ぶ。
- [点群モデルを漏洩なく評価する](point-cloud-evaluation.md)：並べ替え、幾何的な劣化、未知の対象への一般化を分け、分割と前処理を決める。

## 図解で読む四つの研究

- **根拠を探してから答える**：[RAG](../papers/2020/rag.md)。検索した複数の段落を、生成確率へどう組み込むか。
- **コンパイラの判断を学ぶ**：[MLGO](../papers/2021/mlgo.md)。ソース生成との違いと、学習・利用時の流れ。
- **証明器の応答を探索に戻す**：[DeepSeek-Prover-V1.5](../papers/2024/deepseek-prover-v1-5.md)。失敗した証明のどこを残し、どこから再開するか。
- **文章を設計手順へ変える**：[Text2CAD](../papers/2024/text2cad.md)。説明の粒度、スケッチ、押し出し、形状確認を分ける。

各ノートは原論文の読み直しと独自の概念図を組み合わせた解説。図は実測結果や転載図ではなく、詳しい出典と確認範囲は本文・[図の制作情報](../assets/diagrams/README.md)に記す。

## 点群を学ぶ4ステップ

「同じ点を並べ替えた場合」と「測定点が欠けた場合」は、確かめたい性質が違う。点群の表現から、比較可能な評価を組み立てるまでを順に読む。

1. **順序を気にしない集約**：[PointNet](../papers/2017/pointnet.md)。共有する点ごとの処理とmax集約を、小さな数値例で追う。
2. **近くの形を組み合わせる**：[PointNet++](../papers/2017/pointnet-plus-plus.md)。代表点・近傍・局所特徴・階層を分けて理解する。
3. **何に対する頑健性かを決める**：[劣化ベンチマークの比較](../papers/2022/point-cloud-corruptions.md)。似た名前のModelNet-CとModelNet40-Cを、データと指標から区別する。
4. **評価条件を固定する**：[点群評価の実務ノート](point-cloud-evaluation.md)。取得元単位の分割、前処理の学習範囲、保存する記録を整理する。

図と例は公開文献の説明をもとに作成したもの。新しい実験結果や手法の優劣を示すものではない。

<a id="llm-foundations"></a>

## 1. LLMの基礎・推論・実装

**問い：モデル内部の計算と、プロンプトで変える部分を区別できるか。** まず入力から出力までを追い、その後に推論手順を指示する方法を読むと、アーキテクチャの変更と使い方の変更を整理しやすい。手法の名称だけで性能向上を期待せず、試したタスクと条件を確認する。

読む順序：
1. [Transformerの基本構造](../articles/2026/202601.md#transformer-basics)：埋め込み、Attention、出力までの流れを図と説明で追う読書記録。
2. [SCoTの読書記録](../articles/2025/202501.md#strategic-cot)：問題を解く戦略と解答生成を分ける考え方を読む。
3. [TorchCode](../articles/2026/202608.md#torchcode)：演算を自分で実装し、数値・形状・勾配の検査につなげる。

研究結果を評価するときは、[コード最適化の評価](code-optimization-evaluation.md)や[形式証明の検証](formal-proof-validation.md)へ進む。

<a id="code-generation"></a>

## 2. コード生成・コンパイラ・評価

**問い：何を生成し、どの性質を改善したいのか。** ソースコードの書き換え、コンパイラへの指示、変更内容の説明では、出力も成功条件も異なる。ここでは「同じLLMだから」という理由で結果を一括比較せず、タスクを先に分けて読む。

- 最初に：[コード最適化の評価](code-optimization-evaluation.md)。測る目的と比較条件を決める。
- 表現を知る：[IRCoder](../papers/2024/README.md#ircoder)。ソースと中間表現を扱う読書記録へ進む。
- 変更を文章で説明したい：[CommitBERT](../papers/2021/README.md#commitbert) → [RACE](../papers/2022/README.md#race)。コミットメッセージ生成の記録を、コードの実行性能とは別の読み筋としてたどる。

生成物の検査では、テストで確認する性質と形式的に確かめる命題を分ける。[形式証明の検証](formal-proof-validation.md)も参照する。

<a id="formal-proofs"></a>

## 3. 形式証明・Lean

**問い：「通る証明」と「意図した問題への正しい解答」はどう違うか。** 生成された証明だけを見る前に、証明対象の定理文と前提を確認する。成功率を比較するときは、試行回数・探索時間・検証環境もそろえる。

読む順序：
1. [形式証明の検証](formal-proof-validation.md)：何を保存し、どこを確認するかを整理する。
2. [TRIGO](../papers/2023/README.md#trigo) → [TheoremLlama](../papers/2024/README.md#theoremllama)：課題と生成・学習の方法を論文記録から読む。
3. [Leanベンチマークの研究記録](../articles/2025/202510.md#lean-benchmark-summary)：このリポジトリで記録された実験の考え方を読む。元データの再現確認済みという意味ではない。

<a id="cad-3d"></a>

## 4. CAD・3D表現

**問い：欲しいのは見た目、寸法を変えられる設計、それとも空間中の位置か。** 出力が同じ3D表示でも、後で何を編集・測定できるかは異なる。先に利用目的と残したい情報を決めてから手法を読む。

- 最初に：[3D表現とCADの選び分け](cad-representations.md)。寸法変更の例で、必要な表現と検査を考える。
- 設計手順を生成する研究：[CAD-Llama](../papers/2025/README.md#cad-llama)と[AIDL](../papers/undated.md#aidl)の読書記録。
- 画像から作る工程と、コードで形状を編集する工程：[Modly](../articles/2026/202608.md#modly)、[text-to-cad](../articles/2026/202608.md#text-to-cad)の確認済みメモを比較する。

生成コードの成否だけで形状の適合を判断しない。ソースの再実行・形状の測定・用途上の確認をそれぞれ残す。

点を入力として認識・分類する側へ進むなら、上の[点群を学ぶ4ステップ](#点群を学ぶ4ステップ)へ。CAD生成の妥当性と、点群認識の精度・頑健性を同じ評価として扱わない。

<a id="agents-integrations"></a>

## 5. エージェント・外部連携

**問い：何を判断する役割と、どのデータへ接続する仕組みが必要か。** この読み順では、対話画面、開発手順、外部APIへの接続を別の層として扱う。ローカル保存やセルフホストという説明だけで、推論・連携先への送信範囲まで判断しない。

- 対話とツール利用の入口：[LibreChat](../articles/2026/202608.md#librechat)。UIの配置とモデル・実行サービスの配置を区別する。
- 作業手順を明示したい：[agent-skills](../articles/2026/202608.md#agent-skills)。仕様化・テスト・レビューのどこで使うかを考える。
- 外部サービスへ接続したい：[Nango](../articles/2026/202608.md#nango)。接続管理と、サービス固有の処理を分けて読む。
- 長期利用を検討する前に：[ml-intern](../articles/2026/202608.md#ml-intern)。廃止された実装を、現行サービスと混同しないための例。

<a id="research-writing"></a>

## 6. 論文・研究メモの伝え方

**問い：後から読んだ人が、根拠と判断をたどれるか。** 要約には結論だけでなく、何を対象にした結果か、どこが応用例か、まだ確認していない点を残す。図表と文章で同じ数値を使う場合も、更新箇所を追えるようにする。

- 図表を作る前に：[科学論文での図表作成](../papers/undated.md#scientific-figures)。本文との対応や数値・単位の確認に使う。
- 考え方を再利用したい：[デザインパターンの研究整理](../papers/2012/README.md#design-patterns)。文脈・問題・解決の理由を一緒に残す例。
- 実際にメモを書く：[記入方針とひな型](../CONTRIBUTING.md)。出典確認と実行確認、推測と事実を分ける。
- 実験条件を記録する：[点群評価の実務ノート](point-cloud-evaluation.md)。分割・前処理・選択基準を、結果と一緒にたどれる形にする。
