# テーマから読む

月を覚えていなくても、気になった話へ戻れるようにした索引。論文同士をつないで読むと、似た言葉で違うものを測っていたり、使いたい場面にはまだ答えが出ていなかったりする。そういう箇所を横断ノートにまとめている。

まず比較の仕方を知りたいなら、次の四つから。

- [証明器が通した証明をどう確かめるか](formal-proof-validation.md)。証明文より先に、定理文と前提を見る。
- [コード最適化の数字をどう比べるか](code-optimization-evaluation.md)。命令数、サイズ、実行時間のどれを測ったのか。
- [欲しい3Dデータは何か](cad-representations.md)。見た目を作るところと、あとで寸法を変えるところ。
- [点群をどう分けて評価するか](point-cloud-evaluation.md)。同じ物体を別ファイルにしても、未知の物体は増えない。

## 図解で読む四つの研究

検索した段落を生成に使う[RAG](../papers/2020/rag.md)は、まず「検索してから答える」の内側を追う。複数の候補段落があるとき、どの確率を合わせているのかが要所になる。

[MLGO](../papers/2021/mlgo.md)ではコンパイラ内の判断を学ぶ。モデルにソースコードを一式書かせる話とは、任せる範囲が違う。[DeepSeek-Prover-V1.5](../papers/2024/deepseek-prover-v1-5.md)は、証明器の応答を受けてどこから探索をやり直すかに注目すると読みやすい。

[Text2CAD](../papers/2024/text2cad.md)は文章からスケッチと押し出しの操作列を作る。形が出るところまでを追ったら、指定した寸法や編集の意図がどこまで残るかも見ておきたい。

図は各論文の説明をもとに作った概念図で、転載や実測グラフではない。[図の出典と制作情報](../assets/diagrams/README.md)も置いてある。

## 点群を学ぶ4ステップ

出発点は「入力の点に順番は必要か」。そこから近傍、欠損、データ分割へ進むと、モデルの仕組みと評価で気をつけることがつながる。

1. [PointNet](../papers/2017/pointnet.md)では、点ごとに同じ処理をしてmaxでまとめる。小さな数値例で、順番が消える場所を確かめる。
2. [PointNet++](../papers/2017/pointnet-plus-plus.md)では、近くの点を束ねて局所特徴を作る。代表点を選ぶ処理と、近傍を選ぶ処理を分けて読む。
3. [劣化ベンチマークの比較](../papers/2022/point-cloud-corruptions.md)へ。「頑健」という一語では足りない。ModelNet-CとModelNet40-Cは名前も似ているので、データと集計法を見比べる。
4. [点群評価のノート](point-cloud-evaluation.md)で、自分が測りたい「未知」を決める。新しいサンプリングなのか、物体なのか、取得セッションなのかで、分ける単位が変わる。

この順番は公開文献を読むための案。図中の例から手法の優劣や新しい実験結果を読み取ることはできない。

<a id="llm-foundations"></a>

## モデル内部の計算と、使い方の工夫

Transformerの構造が曖昧なら、[入力から出力までの記録](../articles/2026/202601.md#transformer-basics)から戻る。埋め込みやAttentionがどこに入るかを追ってから、[SCoT](../articles/2025/202501.md#strategic-cot)の「戦略を立てて解く」を読むと、モデルを変える話と推論手順を変える話を区別しやすい。

式を読んでも腑に落ちない箇所には[TorchCode](../articles/2026/202608.md#torchcode)のメモがある。演算を実装し、値だけでなく形状と勾配も検査する入口。結果の比較まで進むなら、[コード最適化](code-optimization-evaluation.md)と[形式証明](formal-proof-validation.md)の評価条件も参考になる。手法名だけでは、別のタスクでも効くかは分からない。

<a id="code-generation"></a>

## コードを変える、判断を変える、変更を説明する

この三つを一緒に「コード生成」と呼ぶと、成功の意味がぼやける。

[コード最適化の比較](code-optimization-evaluation.md)は、何を変えて何を測るかを決めるためのノート。[IRCoder](../papers/2024/README.md#ircoder)ではソースと中間表現を扱うが、生成能力が上がることを、そのまま実行性能の向上とは読まない。

コミットメッセージを作りたい場合は、[CommitBERT](../papers/2021/README.md#commitbert)から[RACE](../papers/2022/README.md#race)へ。こちらは変更内容を文章で説明する課題なので、速度の数字から離れて読む。生成物の正しさが気になったら、[テストと形式的な検証の違い](formal-proof-validation.md)も確認する。

<a id="formal-proofs"></a>

## Leanで通った。その定理は、解きたかった問題か

証明の生成に目が行くが、最初に固定したいのは定理文と前提。[検証ノート](formal-proof-validation.md)には、依存する公理や環境を含めて何を保存するかを書いた。成功率を見るときには、試行回数と探索時間も要る。

具体的な課題は[TRIGO](../papers/2023/README.md#trigo)、生成と学習の方法は[TheoremLlama](../papers/2024/README.md#theoremllama)の記録へ。[Leanベンチマークの研究記録](../articles/2025/202510.md#lean-benchmark-summary)も残してある。こちらは当時の実験の考え方を読むためのリンクで、元データを再現確認したという意味ではない。

<a id="cad-3d"></a>

## 見た目ができたあと、何を変えたいか

形を眺めるだけか、穴の間隔を変えたいか。それで必要な出力が変わる。[CADと3D表現のノート](cad-representations.md)では、メッシュ、生成手順、幾何制約を寸法変更の例で比べている。

設計手順を生成する研究は[CAD-Llama](../papers/2025/README.md#cad-llama)と[AIDL](../papers/undated.md#aidl)。道具の使い分けなら、画像から形を作る[Modly](../articles/2026/202608.md#modly)と、コードで形を扱う[text-to-cad](../articles/2026/202608.md#text-to-cad)のメモを並べて読む。ソースが実行できたか、寸法が合ったか、用途に使えるかは、それぞれ確認が必要になる。

点から物体を認識する側に関心があれば、[点群の読み順](#点群を学ぶ4ステップ)へ。生成したCADの妥当性とは別の評価になる。

<a id="agents-integrations"></a>

## エージェントを置く場所と、データが出ていく先

「ローカル保存」と書かれていても、推論や外部連携まで端末内とは限らない。ここは導入前に接続先を追いたい。

- [LibreChat](../articles/2026/202608.md#librechat)：対話画面をどこに置き、モデルやツールをどこで動かすか。
- [agent-skills](../articles/2026/202608.md#agent-skills)：仕様化、テスト、レビューの作業手順をどう渡すか。
- [Nango](../articles/2026/202608.md#nango)：接続管理に任せる部分と、サービスごとに書く処理はどこか。

継続利用を考えるなら、廃止済みの[ml-intern](../articles/2026/202608.md#ml-intern)の記録も参考になる。残っている説明が、今も使えるサービスの説明とは限らない。

<a id="research-writing"></a>

## あとで読み返せるメモにする

結論だけあると、その条件を忘れて使ってしまう。反対に注意書きばかりでも、何を読んだのか思い出せない。対象、根拠、そこから考えたこと、まだ分からない点がたどれればよい。

[科学論文での図表作成](../papers/undated.md#scientific-figures)は、本文と図表の対応や数値・単位を点検するときに。[デザインパターンの研究整理](../papers/2012/README.md#design-patterns)は、文脈と問題と解決の理由を一緒に残す例として読む。実験条件には[点群評価の記録項目](point-cloud-evaluation.md)も使える。

追記の約束と確認コマンドは[CONTRIBUTING](../CONTRIBUTING.md)にまとめた。各ページの見出しを同じにそろえる必要はない。
